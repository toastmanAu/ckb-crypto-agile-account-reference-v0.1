# Threat model

## Security objective

AccountLockV1 protects every cell whose lock args are `0x01 || account_id` while
allowing the account's authenticators, thresholds, recovery policy, and verifier
implementations to evolve in one Type ID state cell. An attacker must not spend
an asset or change that singleton state without satisfying the current policy.

This threat model covers consensus behavior of this repository's scripts and
byte-exact host helpers. It does not cover wallet UI security, credential
storage, browser integrity, RPC trust, transaction-fee policy, or validator
implementation bugs outside the scripts.

## Assets

- Cells protected by AccountLock args.
- Integrity and uniqueness of AccountStateV1.
- Authenticator keys and recovery policy.
- Verifier implementation references.
- Authorization digest and transaction intent.
- Availability within practical CKB cycle and transaction-size limits.

## Trust boundaries

1. A wallet constructs state, witnesses, and proofs from untrusted chain/RPC
   data.
2. AccountLock parses transaction, state, and witness bytes inside CKB-VM.
3. AccountLock resolves verifier code from cell deps.
4. Parent and verifier child communicate through one inherited CKB pipe.
5. Each verifier parses algorithm-specific proof bytes and cryptographic input.
6. The CKB VM and built-in Type ID system script enforce execution and identity.

Verifier code is trusted only by the exact hash stored in the current state.
Host-generated bytes are not trusted by AccountLock merely because they came
from this repository's host library.

## Adversaries

- A transaction author controlling every input, output, dep, header dep, and
  witness except unavailable private signing material.
- A malicious or buggy verifier that exits nonzero, closes a pipe early, hangs
  until cycle exhaustion, or returns malformed behavior.
- A state-substitution attacker presenting a valid AccountStateV1 under another
  Type ID.
- A downgrade attacker selecting unknown algorithms, profiles, ABI versions, or
  stale verifier code.
- A parser adversary supplying truncated, oversized, noncanonical, duplicated,
  or overflow-inducing fields.
- A compromised old authenticator attempting policy rotation after it no longer
  appears in current state.

## Threats and controls

| Threat | Primary controls | Evidence |
|---|---|---|
| Asset transaction mutation after signing | Canonical group sighash and authorization digest bind raw transaction and current state | Host digest tests and VM mutation-family test |
| Foreign or duplicate account state | Account ID is the Type ID script hash; exactly one matching state is resolved | Type ID creation story and foreign-substitution VM test |
| State deletion or unauthorized replacement | Rotation/recovery require one identical Type ID output and sequence +1 | Transition and deletion VM tests |
| Threshold bypass | Sorted unique proof slots, capability filter, checked weight sum, operation threshold | Hybrid and threshold-two VM story |
| Proof transport ambiguity | No argv; one length-delimited VerifierRequestV1 over one inherited pipe | Fixture spawn/pipe VM test |
| Treating verifier failure as success | Weight is added only when `wait` returns child status 0 | Nonzero-exit VM test |
| Verifier-code substitution | State commits exact code hash and hash-type selector; dep resolution requires one match | Verifier-upgrade and state parser tests |
| Unknown-version downgrade | Frozen versions, algorithm IDs, flags, profiles, and ABI parsing | Parser corpus and explicit VM rejection test |
| Integer wrap or length confusion | Checked arithmetic, strict framing, maximum lengths, release overflow checks | Mutation/truncation corpus and release profile |
| WebAuthn replay across account/state/operation | Challenge is the common authorization digest; RP ID, origin hash, UP, and UV are checked | P-256 VM test |
| Premature recovery | Current state recovery flag/threshold plus raw input `since` comparison | Early/mature recovery VM story |
| Stale-state authorization | Digest includes current sequence and current state data hash | Digest tests and exact-outpoint story |

## Denial-of-service considerations

- Proof, aux, state, witness, and request sizes have protocol maxima.
- Authenticator and proof counts are bounded.
- Each selected proof spawns a child and consumes cycles even when invalid.
- PQ verification is materially more expensive than the fixture or P-256 path.
- A wallet must estimate cycles for the exact proof set and avoid unnecessary
  verifier invocations.
- A verifier child cannot turn a nonzero result into weight, but it can consume
  the transaction's remaining cycle budget.

## Residual risks

- No independent audit has been completed.
- RustCrypto ML-DSA and SLH-DSA adapters are not the exact upstream audited CKB
  implementations and do not inherit their review status.
- The SLH-DSA dependency is a release candidate version.
- The WebAuthn JSON parser intentionally supports a strict subset and requires
  wallet compatibility testing.
- Raw `since` comparison enforces the frozen protocol but wallet software must
  construct the intended CKB since encoding correctly.
- Side-channel properties of cryptographic dependencies under CKB-VM have not
  been independently evaluated here.
- Consensus safety ultimately depends on the exact deployed ELF bytes, not the
  source tree or a similarly named crate.

## Review triggers

Repeat threat-model and audit review when any wire byte, digest domain, script
version, algorithm/profile, cryptographic dependency, compiler, linker layout,
spawn/pipe behavior, or deployment artifact changes.
